You are a principal software architect and senior full-stack engineer. Build a production-oriented, multi-tenant School Management SaaS for Bangladesh. Work inside the current repository. C. ARCHITECTURE AND TENANCY — NON-NEGOTIABLE

Use shared MySQL database and shared tenant tables for the initial version.


Central platform tables include platform users, schools, school domains, plans, plan features, subscriptions, platform invoices, platform payments, support tickets and platform activity logs.


Every tenant-owned record MUST include school_id, including users, roles, students, guardians, enrollments, teachers, attendance, examinations, fees, notices, settings, files and logs.


Tenant identification:



Resolve the request hostname to a school domain record.

Reject unknown, inactive, suspended or invalid tenants with safe responses.

Establish immutable request-scoped tenant context.

Never accept school_id from a form, query parameter or arbitrary request header as authoritative.

Derive school identity from the resolved tenant context.

Apply tenant-aware query scopes, policies and service validation.

Restore and clear tenant context correctly in queued jobs and scheduled commands.


Subdomains:



admin.YOUR_DOMAIN for platform administration.

{school-slug}.YOUR_DOMAIN for tenant portal and public website.

Root domain for marketing and registration.


Security:



Global scopes are not the only security boundary.

Every service, policy, export, file download, API endpoint and job must enforce tenant ownership.

Prevent cross-tenant foreign-key associations.

Include tenant ID in cache keys, file paths and job payloads.

Test cross-tenant IDOR attempts.

Parent can access only linked children.

Teacher can access only assigned classes/subjects and authorized records.

Platform support access to school data must be explicit, time-limited, reason-logged and audited.

Do not log passwords, tokens, NID, birth registration numbers, payment secrets or sensitive student data.


Do not build custom cryptography. Use framework encryption and established password hashing.

Database conventions:



InnoDB, utf8mb4.

BIGINT UNSIGNED internal IDs.

Tenant-owned rows have school_id.

Tenant-scoped unique values (admission no, invoice no, receipt no, email/phone where applicable).

Foreign keys and indexes.

Composite indexes for common school/session/class/date queries.

DECIMAL for money and marks.

UTC timestamp storage and Asia/Dhaka display.

Soft delete only where appropriate.

JSON only for flexible configuration or sanitized provider payloads.

Use transactions for multi-step financial and academic operations.


Review composite tenant constraints. A normal foreign key to students.id does not alone prove that the referenced student belongs to the same school. Enforce same-tenant relationships through service validation and, where practical, composite unique keys and composite foreign keys.

I. TESTING AND ACCEPTANCE

Required tests:



Unknown subdomain cannot access a tenant.

Tenant A cannot read/update/delete Tenant B records.

Cross-tenant access is denied for IDs guessed in URL/body.

Tenant isolation also applies to queues, exports, storage, search and notifications.

Parent can access only linked children.

Teacher can access only assigned classes/subjects.

Duplicate attendance is rejected.

Student can have multiple guardians; guardian can have multiple students.

Admission conversion creates correct student, guardian links and enrollment.

Student promotion preserves historical enrollment.

Grading calculations match school-approved fixtures.

Invoice total and outstanding balance calculations are correct.

Partial payment allocations work.

Duplicate gateway callback does not double-credit payment.

Invalid gateway signature is rejected.

Subscription expiry/grace/suspension follows plan policy.

Public website never exposes private records.

Bangla text renders correctly in UI and generated PDFs.


Definition of done:



Responsive UI.

Backend validation and authorization.

Tenant isolation.

Automated tests.

Loading/empty/error states.

Audit logs where appropriate.

No exposed secrets.

Updated docs.
